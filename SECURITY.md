# Security Policy

## Supported Versions

browser-gateway is pre-1.0 and ships from a single release line. Only the latest
published version receives security fixes. Upgrade before reporting an issue
against an older release.

| Version | Supported |
| ------- | --------- |
| Latest `0.4.x` | Yes |
| Older | No |

## Reporting a Vulnerability

Report privately through GitHub Security Advisories:

**https://github.com/browser-gateway/browser-gateway/security/advisories/new**

If you cannot use GitHub, email **hello@browsergateway.com** with `SECURITY` in
the subject line.

Please do not open a public issue, pull request, or discussion for a security
problem. Public disclosure before a fix is available puts every operator running
the gateway at risk.

### What to include

A report is actionable when it contains all of the following. Reports missing
these are usually closed without investigation.

- Affected version, and whether the issue is in the gateway, the dashboard, or
  the CLI
- The specific file, endpoint, or configuration involved
- Reproduction steps, or a proof of concept
- The impact you believe this has, and what an attacker gains
- Any suggested fix, if you have one

### What to expect

- Acknowledgement within 5 business days
- An assessment of severity and whether we accept the report, within 10 business
  days of acknowledgement
- A fix released in the next patch version for accepted high-severity issues, or
  in a subsequent release for lower-severity ones
- Credit in the release notes and the advisory, unless you prefer otherwise

We ask that you give us 90 days from acknowledgement before disclosing publicly,
or until a fix ships, whichever comes first.

## No bug bounty

We do not operate a paid bug bounty program and do not offer payment, swag, or
gift cards for reports. Reports are welcome regardless, and valid ones are
credited publicly.

We do not participate in third-party bug bounty or vulnerability-brokerage
platforms, and do not respond to emails from them.

## Scope

This policy covers the open-source gateway and the hosted cloud service. Both
are reported through the same channels above.

In scope, open source:

- The `browser-gateway` npm package and its published Docker images
- The bundled dashboard served from the gateway
- The CLI
- The MCP server

In scope, hosted cloud service:

- `app.browsergateway.com` and its API at `app-api.browsergateway.com`
- The CDP endpoint at `cdp.browsergateway.io`
- Anything affecting the confidentiality or integrity of customer data:
  cross-workspace access, authentication or session handling, API key and token
  handling, stored browser profiles, session recordings, and billing or wallet
  balances

Cloud findings are treated as higher severity than the equivalent issue in the
self-hosted gateway, because they affect customer data rather than a single
operator's own deployment. Report those first and we will prioritise them.

Out of scope. These are closed without investigation:

- Automated scanner output submitted without a working proof of concept
- Vulnerabilities in upstream dependencies, unless you can demonstrate that
  browser-gateway is actually exploitable through them
- Issues that require the operator to have already been compromised, or that
  require physical or local shell access to the host
- Missing security headers, TLS configuration, or DNS records on
  `browsergateway.com` and `docs.browsergateway.com`. This exclusion does not
  extend to the application at `app.browsergateway.com` or the CDP endpoint
- Denial of service through resource exhaustion, rate limiting, or volumetric
  traffic
- Self-XSS, clickjacking on pages with no sensitive action, or issues only
  reachable with a browser extension installed
- Behaviour of third-party browser providers you route to. The gateway forwards
  bytes to whichever endpoint you configure; the security of that endpoint is
  between you and that provider
- Reports generated by an automated agent with no human verification

### A note on the threat model

This section is about the self-hosted gateway. It does not apply to the hosted
cloud service, where we operate the infrastructure and the assumptions below do
not hold.

browser-gateway is infrastructure you self-host. It assumes the operator
controls the machine it runs on and the provider endpoints it is configured
with. Findings that depend on an attacker already holding one of those is not a
vulnerability in the gateway.

Authentication is opt-in through `BG_TOKEN`. A gateway deployed to a public
network without it is unauthenticated by design and by the operator's choice.
That configuration is documented, not a vulnerability.

### Testing against the cloud service

Test only against workspaces and accounts you own. Do not attempt to access
another customer's data, do not run automated scanners or load generators
against the production endpoints, and do not attempt denial of service. If a
finding appears to expose another customer's data, stop, do not retrieve more
than the minimum needed to demonstrate it, and tell us immediately.

Testing that stays within those bounds is authorised and we will not pursue
action over it.
